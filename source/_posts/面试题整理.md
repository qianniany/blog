# Docker

## 1\.docker和虚拟机的区别是什么?

![image.png](/img/posts/interview/docker/image.png)

### 1\.虚拟化原理：一个 “共享内核”，一个 “模拟硬件”

Docker：不模拟硬件，而是直接使用主机的操作系统内核。容器里只打包应用程序和它需要的依赖库（如 Java 环境、配置文件），相当于 “寄居” 在主机 OS 上的独立进程，被 Docker 引擎隔离管控。

虚拟机：通过 Hypervisor（虚拟化层）模拟出完整的物理硬件（CPU、内存、硬盘），每个虚拟机都要安装独立的操作系统（如 Windows 10、CentOS 7），应用程序运行在这个独立 OS 里，和主机 OS 完全隔离。

### 2\.资源占用：轻量级 vs 重量级

Docker：因为共享主机内核，不需要额外运行一个完整 OS，所以资源消耗极低。比如一个 Nginx 容器只占几 MB 内存，一台主机能同时运行上千个容器。

虚拟机：每个 VM 都有独立的 OS（如 Windows 系统本身就占几 GB 内存），再加上应用消耗，资源开销大。一台主机通常只能运行几十个 VM，多了就会卡顿。

### 3\.启动速度：毫秒级 “秒启” vs 分钟级 “慢启”

Docker：启动容器时，本质是启动一个被隔离的进程，无需启动 OS，所以像打开普通软件一样快（比如 Nginx 容器启动只需 10 毫秒）。

虚拟机：启动时必须先启动独立的 OS（如 Windows 启动需要 1\-2 分钟），再启动应用，整个过程耗时久，适合长期运行，不适合频繁启停。

### 4\.隔离性：“进程隔离” vs “完全隔离”

Docker：隔离性基于 Linux 的 Namespace 和 Cgroups 技术，是 “进程级隔离”—— 容器里的进程只能访问自己的资源，但共享主机内核。如果一个容器被攻击，可能会影响到主机或其他容器（安全性较弱）。

虚拟机：每个 VM 是 “完全隔离” 的，拥有独立的 OS 和硬件资源，相当于一台独立的物理机。即使一个 VM 被入侵，也不会影响其他 VM 或主机（安全性强）。

### 5\.移植性：“一次打包，到处运行” vs “依赖环境”

Docker：容器镜像包含应用和所有依赖，且不依赖主机 OS 的具体配置（只要主机有 Docker 引擎，不管是 Linux、Windows、Mac），都能直接运行，移植性极强（比如开发环境打包的镜像，直接部署到生产环境）。

虚拟机：VM 镜像包含完整 OS，依赖 Hypervisor（如 VMware 的镜像不能直接在 VirtualBox 上运行），且镜像体积大（几个 GB），传输和部署都麻烦，移植性一般。

## 2\. Docker中的镜像是什么?

Docker 镜像的核心结论：**是包含应用程序、依赖库、运行环境（如操作系统内核片段、配置文件）的只读模板，是创建 Docker 容器的 “蓝图”—— 容器就是镜像运行起来的实例（可读写副本）**

### 镜像的 4 个核心特性

#### 1\. 只读性（核心属性）

镜像构建后是**完全只读**的，不能直接修改里面的文件（比如不能直接编辑镜像里的 Nginx 配置）。如果需要修改，只能基于原镜像创建 “新镜像”（通过 Dockerfile 叠加修改），或启动容器后在容器内修改（容器是镜像的可读写副本，修改仅作用于容器，不影响原镜像）。

#### 2\.分层存储（高效复用的关键）

镜像不是单个文件，而是由多个 “只读层” 叠加而成，像 “叠积木” 一样：

- 底层是基础镜像层（如 CentOS、Alpine 系统的核心文件）；

- 上层是应用相关层（如安装 Nginx、配置文件、部署应用代码）；

- 不同镜像可共享底层层（比如两个 Nginx 镜像都基于同一个 CentOS 基础层，只需存储一次基础层，节省磁盘空间）。

举个例子：`nginx:alpine` 镜像的分层结构：

- 底层：Alpine Linux 系统的核心层（约 5MB，提供基础运行环境）；

- 中层：安装 Nginx 软件的依赖层（如 libc 库）；

- 上层：Nginx 二进制文件、默认配置文件层。

#### 3\. 镜像是容器的 “模板”（容器是镜像的 “实例”）

镜像和容器的关系，就像 “类” 和 “对象” 的关系：

- 镜像：静态的模板（比如 “iPhone 设计图纸”），只定义了 “跑起来需要什么”；

- 容器：镜像运行后的动态实例（比如 “具体的 iPhone 手机”），是可读写的，能执行应用程序。

比如：执行 docker run nginx 命令时，Docker 会先检查本地是否有 nginx 镜像，没有就从 Docker Hub 下载，然后基于该镜像创建一个容器（可读写副本），再启动容器里的 Nginx 服务。

#### 4\.标准化命名与版本（方便管理和使用）

镜像有固定的命名规范，格式为：\[仓库地址/\]\[用户名/\]\[镜像名\]:\[标签\]

- 标签（Tag）：用于区分镜像版本（默认标签为 latest，表示最新版）；

- 示例：
  - nginx:1\.24：Docker Hub 官方的 Nginx 镜像，版本 1\.24；

  - mycompany/redis:6\.2：自定义仓库的 Redis 镜像，版本 6\.2；

  - localhost:5000/mysql:8\.0：本地私有仓库的 MySQL 镜像，版本 8\.0。

## 3\.运行Docker容器的命令是什么?

```Bash
docker run [选项] 镜像名[:标签] [容器内执行的命令]
```

- 「镜像名 \[: 标签\]」：指定要运行的镜像（标签可选，默认 `latest`，如 `nginx:1.24` 而非 `nginx`）；

- 「容器内执行的命令」：可选，默认执行镜像的「入口命令」（如 Nginx 镜像默认启动 `nginx` 服务）；

- 「选项」：最关键的部分，控制容器运行模式、资源、网络等，下面重点讲解。

```Plain Text
# 运行 Nginx 容器（默认标签 latest，前台启动）
docker run nginx
```

**直接运行镜像，容器在「前台」启动（终端被占用，关闭终端则容器停止）**

```Plain Text
# 后台运行 Nginx 容器，标签指定 1.24（推荐显式指定版本，避免兼容性问题）
docker run -d --name my-nginx nginx:1.24
```

**用 \*\***`-d`\***\*（detach，分离模式）让容器在后台运行，不占用终端：**

- 关键参数：`--name my-nginx` 给容器命名（方便后续管理，如停止、删除），否则 Docker 会自动生成随机名称；

- 验证：`docker ps` 查看运行中的容器，能看到 `my-nginx` 及状态；

- 停止：`docker stop my-nginx`（用名称或容器 ID 均可）。

```Plain Text
# 主机 8080 端口 → 容器 80 端口，后台运行并命名
docker run -d -p 8080:80 --name my-nginx nginx:1.24
```

**端口映射（\-p，外部访问容器必备）**

容器内的服务（如 Nginx 的 80 端口）默认无法被主机访问，需用 `-p 主机端口:容器端口` 映射：

```Markdown
# 主机 ./nginx/conf 目录 → 容器 /etc/nginx/conf.d（Nginx 配置目录）
# 主机 ./nginx/html 目录 → 容器 /usr/share/nginx/html（静态文件目录）
docker run -d -p 8080:80 --name my-nginx \
  -v $(pwd)/nginx/conf:/etc/nginx/conf.d \
  -v $(pwd)/nginx/html:/usr/share/nginx/html \
  nginx:1.24
```

**目录挂载**

用 `-v 主机目录:容器目录` 将主机目录挂载到容器，实现「数据持久化」（容器删除后数据不丢失）或「文件共享」（主机修改文件，容器内实时生效）：

## 4\.说出几个DockerFile的常见指令

### 1\. `FROM`：指定基础镜像（必备，第一条指令）

指定构建当前镜像的「基础镜像」，所有后续指令都基于这个基础镜像执行（相当于 “继承” 一个已有的模板）

```Plain Text
# 基于轻量的 Alpine Linux 基础镜像（适合追求小体积）
FROM alpine:3.19

# 基于 Ubuntu 基础镜像（适合需要完整系统环境）
FROM ubuntu:22.04

# 基于 Java 17 运行时镜像（适合 Java 应用）
FROM openjdk:17-jdk-slim
```

### 2\.`WORKDIR`：设置工作目录

指定容器内的「工作目录」，后续的 `RUN`、`COPY`、`CMD` 等指令都会基于这个目录执行（相当于 `cd` 到该目录）。

```Plain Text
# 设置工作目录为 /app（容器内），不存在会自动创建
WORKDIR /app

# 后续命令会在 /app 目录下执行（无需写绝对路径）
COPY app.jar ./  # 等价于 COPY app.jar /app/
```

### 3\. `COPY`：复制本地文件到镜像

将「本地主机的文件 / 目录」复制到「镜像的指定目录」（仅复制，不解压、不下载）。

```Markdown
# 复制本地当前目录的 app.jar 到镜像的 /app 目录
COPY app.jar /app/

# 复制本地 ./src 目录下的所有文件到镜像的 /app/src 目录
COPY src/ /app/src/

# 复制时指定文件所有者（避免权限问题）
COPY --chown=1000:1000 config.yml /app/conf/
```

### 4\. `RUN`：执行构建时命令

在「镜像构建阶段」执行命令（如安装软件、编译代码），执行结果会被打包到镜像中。

- Shell 格式：`RUN 命令`（如 `RUN apt install -y nginx`）；

- Exec 格式：`RUN ["可执行文件", "参数1", "参数2"]`（如 `RUN ["npm", "install"]`，避免 Shell 解析问题）。

```Markdown
# 安装 Nginx（Ubuntu 基础镜像）
RUN apt update && apt install -y nginx && rm -rf /var/lib/apt/lists/*

# 安装 Node.js 依赖（Shell 格式）
RUN npm install --production

# Exec 格式（适合特殊字符场景，如包含空格、引号）
RUN ["pip", "install", "-r", "requirements.txt"]
```

### 5\.`ADD`：复制 \+ 解压 / 下载文件（`COPY` 增强版）

功能比 `COPY` 多两个：① 自动解压本地压缩包（如 `.tar.gz`、`.zip`）到目标路径；② 下载网络文件到镜像（不推荐，下载用 `RUN wget` 更灵活）。

```Plain Text
# 复制并自动解压本地 app.tar.gz 到镜像的 /app 目录（解压后去掉 .tar.gz 后缀）
ADD app.tar.gz /app/

# 下载网络文件到镜像的 /tmp 目录（不推荐，建议用 RUN wget）
ADD https://example.com/config.yml /tmp/
```

### 6\.`ENV`：设置环境变量

定义「环境变量」，该变量在「镜像构建阶段」和「容器运行阶段」都生效（如配置软件路径、应用端口）。

```Markdown
# 设置 Java 环境变量（配合 openjdk 基础镜像）
ENV JAVA_HOME=/usr/local/openjdk-17
ENV PATH=$JAVA_HOME/bin:$PATH

# 设置应用端口和日志目录（容器运行时可引用）
ENV APP_PORT=8080 LOG_DIR=/app/logs
```

### 7\. `EXPOSE`：声明容器端口

「声明」容器运行时会监听的端口（仅为文档说明，不实际映射端口到主机）。

```Plain Text
# 声明容器监听 8080 端口（tcp 协议）
EXPOSE 8080

# 声明多个端口（tcp + udp）
EXPOSE 80/tcp 53/udp
```

### 8\.`CMD`：指定容器启动命令（可被覆盖）

指定容器「启动时执行的默认命令」，如果 `docker run` 命令后带了其他命令，会覆盖 `CMD` 的默认命令。

```Python
# 启动 Java 应用（Exec 格式，推荐）
CMD ["java", "-jar", "/app/app.jar"]

# 启动 Nginx（Shell 格式，适合需要 Shell 解析的场景）
CMD nginx -g "daemon off;"  # Nginx 默认后台运行，需关闭后台模式才能前台运行
```

### 9\.`ENTRYPOINT`：指定容器入口命令（不可被覆盖）

指定容器的「入口命令」，优先级高于 CMD，且不会被 docker run 的命令覆盖（仅能追加参数）。

```Python
# 入口命令为 java -jar，CMD 传默认参数
ENTRYPOINT ["java", "-jar"]
CMD ["/app/app.jar"]  # 默认参数，容器启动时执行 java -jar /app/app.jar

# 启动时追加参数（覆盖 CMD 的默认参数）
# docker run my-java-app /app/app.jar --port 8081 → 执行 java -jar /app/app.jar --port 8081
```

### 10\.VOLUME：声明数据卷（持久化）

声明容器内的「数据卷挂载点」，用于持久化数据（容器删除后数据不丢失，可共享给其他容器）。

```Plain Text
# 声明 /app/data 为数据卷（存储应用数据）
VOLUME /app/data

# 声明多个数据卷（如日志、数据）
VOLUME ["/app/logs", "/app/data"]
```

### 11\. `USER`：指定运行用户

指定容器启动时的「运行用户」（默认是 root 用户，存在安全风险，建议用普通用户）

```Plain Text
# 先创建普通用户（root 权限执行）
RUN groupadd -r appuser && useradd -r -g appuser appuser

# 切换到 appuser 用户（后续命令和容器启动都用该用户）
USER appuser

# 启动应用（以 appuser 身份运行，避免 root 权限风险）
CMD ["java", "-jar", "/app/app.jar"]
```

### 12\. `LABEL`：添加镜像元数据

给镜像添加「元数据标签」（如作者、版本、描述），方便管理镜像（通过 `docker inspect` 查看）。

```Plain Text
LABEL author="dev@example.com"
LABEL version="1.0.0"
LABEL description="Java 应用镜像（基于 openjdk 17）"
```

## 5\.COPY和ADD的区别

两者核心都是「将文件复制到镜像」，但 `COPY` 是「纯复制工具」，`ADD` 是「复制 \+ 额外功能工具」，**优先用 COPY（功能明确无歧义），仅在需要「本地压缩包自动解压」时用 ADD**

![image.png](/img/posts/interview/docker/image%201.png)

- 90% 的复制场景用 `COPY`：功能明确，无隐含行为，避免因 ADD 的解压 / 下载功能导致意外问题（如误解压非预期的压缩包）；

- 仅当需要「本地压缩包自动解压」时用 `ADD`：这是 ADD 最有价值的场景，其他情况一律用 COPY。

## CMD和ENTRYPOINT的区别

两者都是「定义容器启动命令」，但 **CMD 是「默认命令 / 参数」（可直接覆盖），ENTRYPOINT 是「入口命令」（不可直接覆盖，仅能追加参数）**，生产环境常组合使用（ENTRYPOINT 固定命令，CMD 传默认参数）。

## 6\.Docker中的数据卷是什么，有什么作用?

Docker 数据卷（Volume）的核心结论：**是 Docker 管理的「独立于容器生命周期的共享存储空间」，本质是宿主机上的一个目录 / 文件，但由 Docker 统一管理，可挂载到一个或多个容器中，实现数据持久化、共享和隔离**。

通俗比喻：容器是 “临时房子”，数据卷是 “独立于房子的保险柜”—— 房子（容器）可以拆了重建（删除 / 重启容器），但保险柜（数据卷）里的东西（数据）不会丢，还能让多个房子（容器）共用这个保险柜。

### 数据卷的 3 个核心特性（理解本质）

1. **独立生命周期**：数据卷的创建、删除与容器无关（容器删除后，数据卷仍存在，数据不丢失）；

2. **双向共享**：挂载数据卷的容器与宿主机之间、容器与容器之间，可通过数据卷双向读写数据（同步更新）；

3. **Docker 统一管理**：数据卷由 Docker 引擎管理，存储路径默认在宿主机的 `/var/lib/docker/volumes/`（无需用户手动创建目录，避免路径混乱）；

4. **隔离性**：不同数据卷之间相互独立，数据不会混淆（如 MySQL 数据卷和 Nginx 日志卷分开管理）

很多人会混淆数据卷（Volume）和绑定挂载（Bind Mount），两者都能实现数据共享，但核心差异在「管理方式」和「生命周期」：

## 7\.请简要介绍 Docker 网络的几种模式

Docker 网络的核心作用是 **实现容器间、容器与宿主机 / 外网的连通与隔离**，默认提供 5 种核心网络模式，每种模式对应不同场景，以下是 **简洁明了的模式介绍 \+ 适用场景**

![image.png](/img/posts/interview/docker/image%206.png)

### 各模式简要拆解（重点抓核心）

#### bridge 模式（默认首选）

- 启动容器时未指定网络，默认加入 `docker0` 桥接网络；

- 容器有独立私有 IP（如 `172.17.0.x`），Docker 做 NAT 转发实现外网访问；

- 同一 `bridge` 网络下的容器可通过 IP 或容器名互通。

#### host 模式（性能优先）

- 容器直接 “占用” 宿主机的网络端口（如容器启动 80 端口，宿主机 80 端口直接被占用）；

- 无网络隔离开销，性能最好，但端口冲突风险高（多个容器不能用同一端口）。

#### none 模式（完全隔离）

- 仅提供本地回环网络（容器内只能访问自身），无法访问外网或其他容器；

- 适合不需要网络的纯本地任务（如生成文件、数据计算）。

#### container 模式（容器共享网络）

- 例如：`docker run --net=container:容器名 镜像`，新容器复用目标容器的网络；

- 两容器共享 IP、端口、网络配置，如同 “一个容器的两个进程”，通信延迟极低。

#### 自定义 Bridge 模式（隔离优先）

- 手动创建：`docker network create my-network`，容器加入时指定 `--net=my-network`；

- 优势：不同自定义网络的容器默认不通（隔离性强），支持用容器名直接访问（DNS 自动解析），比默认 `bridge` 更灵活。

### 快速选型原则

- 常规多容器协同（如 Web\+DB）→ `bridge`（默认）；

- 多环境 / 多项目隔离 → 自定义 Bridge；

- 高性能无端口冲突 → `host`；

- 容器紧密协同（如主从、代理）→ `container`；

- 无需网络 → `none`。

## 8\.如何创建一个自定义的 Docker 网络?

自定义网络默认是 `bridge` 类型（最常用，适合单机容器隔离），也支持 `overlay`（跨主机集群）等类型，这里重点讲单机常用的 `bridge` 类型。

### 一\.创建自定义网络

#### 1\.基础用法（默认配置，快速创建）

语法：`docker network create 自定义网络名`

```Plain Text
# 创建一个名为 "my-app-network" 的自定义桥接网络（默认配置）
docker network create my-app-network
```

- 特点：Docker 自动分配子网（默认 `172.18.0.0/16` 这类网段）、网关，无需手动配置；

- 适用场景：快速实现多容器隔离（如开发环境专属网络）。

#### 2\.进阶用法（自定义子网、网关，避免冲突）

```Plain Text
# 创建自定义网段（192.168.100.0/24）和网关（192.168.100.1）的网络
docker network create \
  --driver bridge \  # 网络类型（默认 bridge，可省略）
  --subnet 192.168.100.0/24 \  # 自定义子网（必须是 CIDR 格式）
  --gateway 192.168.100.1 \    # 自定义网关（子网内的可用 IP）
  my-app-network-2
```

- 关键参数：
  - `--driver bridge`：指定网络类型为桥接（单机默认，可省略）；

  - `--subnet`：自定义网段（如 `192.168.xxx.0/24`），避免和其他网络冲突；

  - `--gateway`：网段的网关 IP（需在子网范围内）。

### 二\.让容器加入自定义网络

#### 1\.创建容器时直接加入

语法：`docker run --net 自定义网络名 ...`

### 三、实用：自定义网络的核心优势（实战验证）

#### 容器名互通（DNS 解析）

自定义网络相比默认 `bridge` 网络，最大优势是 **支持容器名 DNS 解析**（无需 IP 即可通信）和 **强隔离性**（不同自定义网络容器默认不通）。

```Plain Text

```

#### 异网隔离（不同自定义网络容器不通）

```Plain Text

docker network create my-other-network

# 启动一个容器加入 my-other-network
docker run -d --name isolated-container --net my-other-network nginx:1.24

# 进入 my-nginx（my-app-network），ping isolated-container（my-other-network）

```

### 五、注意事项（避坑必备）

1. **网络隔离性**：不同自定义网络的容器默认不能通信（强隔离），如需通信需手动 `docker network connect` 加入同一网络；

2. **容器名唯一**：同一自定义网络内，容器名不能重复（否则无法加入）；

3. **子网冲突**：手动指定 `--subnet` 时，需避免和宿主机网段、其他网络网段冲突（如宿主机是 `192.168.1.0/24`，自定义子网可设 `192.168.100.0/24`）；

4. **删除网络前提**：删除网络前，需确保该网络下无运行中的容器（否则报错，需先停止容器或断开网络）；

5. **端口映射**：自定义网络不影响容器的端口映射（`-p 主机端口:容器端口`），外网仍可通过宿主机端口访问容器。

## 9\.什么是docker\-compose?

Docker Compose 是 Docker 官方推出的 **多容器应用编排工具**—— 核心作用是用一个 `docker-compose.yml` 配置文件，定义多个关联容器（如 Web 服务 \+ 数据库 \+ 缓存）的启动参数、网络、数据卷等，再通过一条命令实现 “一键启动 / 停止 / 销毁” 所有容器，解决多容器协同的配置繁琐问题。

通俗比喻：之前启动多容器（如 Nginx\+MySQL\+Redis），需要分别执行 `docker run` 写一堆参数（端口、网络、挂载），还得记顺序；Docker Compose 就像 “总开关”，把所有容器的配置写在一个文件里，执行 `docker-compose up` 就能一次性启动所有服务，执行 `docker-compose down` 就能一键清理，不用逐个操作。

### 一、核心价值（解决什么问题？）

1. **简化配置**：用一个 YAML 文件（`docker-compose.yml`）统一管理所有容器的配置（端口、网络、数据卷、环境变量等），无需记忆多条 `docker run` 命令；

2. **一键操作**：单条命令实现 “启动所有容器”“停止所有容器”“重建容器”，无需逐个执行 `docker start/stop/rm`；

3. **容器协同**：自动处理容器依赖（如先启动数据库，再启动依赖数据库的 Web 服务）、网络连通（默认加入同一自定义网络，容器名可直接通信）；

4. **环境一致性**：配置文件可版本控制（如 Git 管理），团队成员拉取代码后，执行 `docker-compose up` 即可快速搭建一致的开发 / 测试环境，避免 “我这能跑，你那跑不了”。

### 二、核心组件：`docker-compose.yml` 配置文件

所有容器的配置都写在 `docker-compose.yml` 中，核心结构包含 4 个部分（最常用）：

- `version`：指定 Compose 文件版本（需与 Docker 版本兼容，推荐 `3.x`）；

- `services`：定义每个容器（服务）的配置（如镜像、端口、挂载、环境变量等）；

- `networks`：定义自定义网络（默认会创建一个同名网络，所有服务自动加入）；

- `volumes`：定义数据卷（实现数据持久化）

```YAML
# 1. Compose 文件版本（3.x 兼容大部分 Docker 版本）
version: '3.8'

# 2. 定义所有容器（服务）
services:
  # 服务1：Nginx（Web 服务）
  nginx:
    image: nginx:1.24  # 镜像名+版本
    ports:
      - "80:80"  # 端口映射（主机80→容器80）
    volumes:
      - ./nginx/html:/usr/share/nginx/html  # 绑定挂载（本地静态文件→容器）
      - nginx-logs:/var/log/nginx  # 数据卷（日志持久化）
    networks:
      - my-app-network  # 加入自定义网络
    restart: always  # 容器退出自动重启

  # 服务2：MySQL（数据库服务）
  mysql:
    image: mysql:8.0
    ports:
      - "3306:3306"
    environment:
      - MYSQL_ROOT_PASSWORD=123456  # 环境变量（根密码）
      - MYSQL_DATABASE=myapp  # 自动创建数据库
    volumes:
      - mysql-data:/var/lib/mysql  # 数据卷（数据持久化）
    networks:
      - my-app-network
    restart: always

# 3. 定义数据卷（全局复用）
volumes:
  nginx-logs:  # 对应 Nginx 的日志卷
  mysql-data:  # 对应 MySQL 的数据卷

# 4. 定义自定义网络（所有服务自动加入，支持容器名通信）
networks:
  my-app-network:
```

## 1\.什么是倒排索引?

倒排索引（Inverted Index）是**搜索引擎、全文检索系统（如 Elasticsearch、Solr）的核心数据结构**，核心作用是「快速根据 “关键词（词条）” 找到包含该关键词的 “文档”」—— 和我们熟悉的 “正排索引” 是反向逻辑，用通俗的类比就能轻松懂：

![image.png](/img/posts/interview/elasticsearch/image%202.png)

倒排索引本质是一张「词条 \- 文档映射表」，主要包含两部分：

**1\.词典（Dictionary）**：所有文档中提取的 “去重关键词（词条）” 集合（比如 “苹果”“喜欢”“好吃”）；

**2\.倒排表（Posting List）**：每个词条对应的 “文档信息列表”—— 至少包含「文档 ID」（哪篇文档），还可能包含「词频」（词条在文档中出现次数）、「位置」（词条在文档中的具体位置）等，用于排序和精准匹配。

例如：

![image.png](/img/posts/interview/elasticsearch/image%203.png)

**总结**

倒排索引的核心逻辑是「从词条找文档」，是全文检索的 “速度基石”—— 没有它，我们在海量数据中搜索关键词（比如在 100 万篇文章中找 “人工智能”），可能需要几分钟甚至几小时；有了它，只需毫秒级就能完成。

## 2\.ES中的文档、字段、索引分别是什么?

![image.png](/img/posts/interview/elasticsearch/image%201.png)

1\.索引:索引是 ES 中 **逻辑上的 “数据容器”**，用于存储一组「结构相似、业务相关」的文档。比如 “电商商品数据”“用户行为日志”“文章内容”，会分别存在不同的索引中。

2\.文档:文档是 ES 中 **最小的数据存储单元**，所有数据都以「JSON 格式」存储在文档中 ——JSON 天然适合存储半结构化数据，灵活且易扩展（无需像 MySQL 那样提前定义所有列）。

```JSON
{
  "_id": "1001",  // 文档唯一ID（手动指定为商品ID）
  "name": "Apple iPhone 15",  // 字段：商品名称
  "price": 5999.00,  // 字段：商品价格
  "category": "手机",  // 字段：商品分类
  "stock": 120,  // 字段：库存数量
  "create_time": "2024-01-15T08:30:00"  // 字段：创建时间
}
```

3\.字段:字段是文档中的「一个键值对（key\-value）」，是 ES 中「数据的最小粒度」—— 比如上面文档中的 name“商品名称”、price“商品价格”，都是字段。

## 3\.使用用ES的时候你用的什么分词器，包含几种模式?

### **核心:IK 分词器（中文首选）**

##### ik_max_word 模式（细粒度分词，默认推荐）

**定义**：对文本进行「最细粒度拆分」，穷尽所有可能的分词组合，确保不遗漏任何潜在关键词，优先保证「召回率」（能搜到尽可能多的相关结果）。

对文本「苹果手机 15Pro 官方旗舰」分词:

苹果、手机、15、pro、15pro、官方、旗舰、官方旗舰

##### ik_smart 模式（粗粒度分词，高效简洁）

**定义**：对文本进行「最粗粒度拆分」，仅保留最核心的分词结果，不重复拆分，优先保证「效率」（分词速度快，结果简洁）。

对文本「苹果手机 15Pro 官方旗舰」分词:

苹果手机、15pro、官方旗舰

### **辅助: 拼音分词器（pinyin\-analyzer）**

将中文转换为拼音，支持「全拼、简拼、首字母、拼音首字母组合」等模式，搭配 IK 分词器使用，实现 “中文 \+ 拼音” 双检索。

其它分词器:

### Standard 分词器（ES 默认分词器）

仅支持「单字分词」（中文）和「按空格 / 标点分词」（英文），无复杂逻辑。

对「苹果手机 15Pro」分词：

苹、果、手、机、1、5、p、r、o

### Keyword 分词器（无模式，精确匹配）

不分词，将整个文本作为「一个完整词条」存储，仅支持精确匹配。

## 5\.match查询和term查询的区别?

**match 查询**：对查询词分词后，匹配包含任一 / 全部词条的文档（适合全文搜索）；

**term 查询**：不对查询词分词，将其作为完整词条，精确匹配文档中的字段值（适合精确筛选）。

![image.png](/img/posts/interview/elasticsearch/image%206.png)

坑 1：用 term 查询`text`字段 → 大概率无结果（text 字段存储时分词，term 查询不分词，无法匹配）；

坑 2：用 match 查询`keyword`字段 → 需查询词与字段值完全一致（keyword 字段不分词存储，match 查询会分词，但分词后只有完全匹配才生效，相当于 “多此一举”）；

坑 3：忽略大小写 / 空格 → term 查询大小写、空格敏感（如查询 “手机” 和 “手机 ”（带空格）是两个不同词条），match 查询因分词可能忽略（取决于分词器）。

实际业务中常结合两者使用：**match 全文搜索 \+ term 精确筛选**（先搜后筛，提升结果精准度）。

```JSON
POST /product/_search
{
  "query": {
    "bool": {
      "must": [{"match": {"name": "苹果"}}],  // 全文搜索“苹果”
      "filter": [{"term": {"category": "手机"}}]  // 精确筛选“手机”分类
    }
  }
}
```

## 6\.ES如何实现分页查询?

### 1\. from\+size：最简单的浅分页（入门首选）

**核心原理**

类似 MySQL 的 `LIMIT from, size`：`from` 表示「跳过的条数」，`size` 表示「当前页条数」；

执行流程：ES 会先查询出前 `from+size` 条数据，排序后跳过前 `from` 条，返回剩下的 `size` 条；

限制：ES 默认通过 `index.max_result_window` 限制 `from+size ≤10000`（避免深度分页拖垮集群）。

```JSON
POST /product/_search
{
  "query": {
    "match_all": {}  // 匹配所有商品（可替换为业务查询条件）
  },
  "sort": [{"create_time": "desc"}],  // 排序字段（必须指定，否则分页顺序可能乱）
  "from": 10,  // 跳过前 10 条（第 1 页 from=0，第 2 页 from=10，以此类推）
  "size": 10   // 当前页返回 10 条
}
```

- 优点：配置简单、支持随机跳页（如直接从第 1 页跳第 5 页）、开发成本低；

- 缺点：深度分页性能差（如 `from=10000` 时，ES 需扫描 10010 条数据，排序后丢弃前 10000 条，浪费资源）；超过 10000 条会报错（需手动修改 `index.max_result_window`，但不推荐）。

### 2\.scroll：海量数据分页（批量导出首选）

**核心原理**

本质是「数据快照」：首次查询时，ES 会创建一个包含查询结果的快照（scroll_id），后续分页仅需通过 `scroll_id` 从快照中拉取数据；

快照有效期：需指定 `scroll` 参数（如 `scroll: "1m"` 表示快照保留 1 分钟），过期后快照自动删除；

特点：不支持实时数据（快照创建后，新增 / 修改的数据不会体现在分页结果中），但性能稳定，适合批量处理。

- 优点：支持百万级数据分页、性能稳定（无需扫描大量数据排序）、适合批量导出；

- 缺点：不支持实时数据、不支持随机跳页（只能顺序拉取）、占用集群快照资源（需合理设置有效期）。

### **3\.search_after：深分页 \+ 实时场景（生产首选）**

**核心原理**

基于「上一页最后一条数据的排序字段值」分页，避免计算前 N 条数据；

核心要求：必须指定「唯一排序字段」（如 `_id` \+ 时间字段），确保每页数据的「锚点」唯一；

执行流程：首次查询返回第 1 页数据，同时记录最后一条数据的排序字段值；下一页查询时，通过 `search_after` 参数传入该值，ES 直接从该锚点向后拉取数据。

- 优点：支持深度分页（百万级数据无压力）、性能优异（无需扫描前 N 条）、实时性强（默认包含新增数据，结合 PIT 可保证一致性）；

- 缺点：不支持随机跳页（只能顺序下拉刷新，如从第 1 页到第 2 页，不能直接跳第 5 页）、需维护排序字段的锚点值。

## 8\.怎么在ES中组合多个查询条件?

在 Elasticsearch（ES）中组合多个查询条件，核心是使用 **布尔查询（bool query）**，它通过 must、should、must_not、filter 四个子句灵活组合多条件，同时支持嵌套查询、范围查询等复杂场景。以下是详细的用法、场景示例和注意事项，覆盖绝大多数业务需求。

![image.png](/img/posts/interview/elasticsearch/image%205.png)

**核心原则**

需影响相关性评分（如搜索结果排序）：用 must/should；

仅筛选数据（无评分需求）：用 filter/must_not（性能更优，缓存筛选结果）；

多条件组合时，可嵌套多个 bool query 实现复杂逻辑。

## 9\.全文检索查询结果默认是如何排序的，如何控制这个顺序?

### 1\.默认排序：基于「相关性评分（\_score）」降序

\_score 是 ES 自动计算的浮点数（默认范围 0\~1，特殊场景可能大于 1），用于量化「文档与查询条件的匹配程度」。比如搜索 “华为手机”，包含完整短语 “华为手机” 的文档，\_score 会高于只包含 “华为” 或 “手机” 单个词的文档。

计算逻辑:

**ES 5\.0\+**：默认用 `BM25` 算法（更精准，对长文本更友好）；

**ES 5\.0 之前**：默认用 `TF-IDF` 算法（经典算法，易理解）。

两种算法的核心思想一致，都是基于 3 个维度：

![image.png](/img/posts/interview/elasticsearch/image.png)

**无评分排序的默认情况:**

如果查询中只有「过滤条件」（如 filter、must_not），没有「评分条件」（如 must、should），ES 不会计算 \_score（默认 \_score=0），此时默认排序为：**按文档的「内部 ID（\_id）」升序排列**（\_id 是 ES 自动生成或用户指定的唯一标识）。

### 2\.自定义排序：控制排序顺序的 3 种核心方式

实际业务中，常需要按「业务规则」排序（如按价格、销量、发布时间），而非单纯的相关性。ES 支持通过 sort 参数灵活控制排序，核心分为 3 类场景：

#### 1\.sort排序

直接指定字段和排序方向（asc 升序、desc 降序），支持 keyword、date、数字、\_id 等字段（**text 字段默认不支持排序，需用 keyword 子字段**）

当单个字段排序出现 “并列”（如多个商品价格相同）时，可叠加多个排序字段，按优先级依次排序 —— 先按第一个字段排序，第一个字段值相同的文档，再按第二个字段排序，以此类推。

```JSON
POST /product/_search
{
  "query": {
    "match": { "name": "华为手机" }
  },
  "sort": [
    { "sales": { "order": "desc" } },  // 第一优先级：销量降序
    { "price": { "order": "asc" } },   // 第二优先级：价格升序
    { "_id": { "order": "asc" } }      // 第三优先级：ID升序（兜底，确保排序稳定）
  ]
}
```

#### 2\.自定义相关性评分（`function_score`）排序（业务加权）

如果需要「相关性 \+ 业务规则」结合排序（如 “搜索相关性 70% \+ 销量 30%”），可通过 function_score 重写 \_score，实现自定义加权排序。

##### 固定权重加权（如广告商品优先）

```JSON
POST /product/_search
{
  "query": {
    "function_score": {
      "query": { "match": { "name": "手机" } },  // 原始全文检索查询
      "functions": [
        // 满足条件的文档，加权因子为 2
        { "weight": 2, "filter": { "term": { "is_ad": true } } }
      ],
      "boost_mode": "multiply"  // 加权方式：原始评分 × 权重（默认值）
    }
  }
}
```

##### 字段值因子加权（如销量越高，权重越高）

```JSON
POST /product/_search
{
  "query": {
    "function_score": {
      "query": { "match": { "name": "零食" } },
      "functions": [
        {
          "field_value_factor": {
            "field": "sales",  // 基于销量字段加权
            "factor": 0.1,     // 缩放因子（降低销量对评分的影响）
            "modifier": "sqrt" // 修饰符：sqrt（开根号），可选值：log、log1p、square等
          }
        }
      ],
      "boost_mode": "sum"  // 加权方式：原始评分 + 字段值计算结果
    }
  }
}
```

##### 脚本自定义加权（复杂业务规则）

```JSON
POST /product/_search
{
  "query": {
    "function_score": {
      "query": { "match": { "name": "图书" } },
      "functions": [
        {
          "script_score": {
            "script": {
              "source": "doc['good_rate'].value * 5 + doc['sales'].value / 1000"  // 自定义脚本
            }
          }
        }
      ],
      "boost_mode": "sum"  // 原始评分 + 脚本计算结果
    }
  }
}
```

# RabbitMQ

## 1\. 介绍一下RabbitMQ的核心组件和工作原理

**组件**

![image.png](/img/posts/interview/rabbitmq/image.png)

**工作原理**

#### 初始化准备（提前配置）

1. 生产者（订单服务）、消费者（物流服务、积分服务）与 RabbitMQ Broker 建立 TCP 连接，再创建 Channel（信道）；

2. 在 Broker 中创建 Virtual Host（如order\-vhost），并在该空间下声明 3 个组件：
   - 交换机：order\-exchange（类型 Topic）；

   - 队列：logistics\-queue（物流队列）、points\-queue（积分队列）；

   - 绑定：
     - order\-exchange 绑定 logistics\-queue，BindingKey 设为order\.\#；

     - order\-exchange 绑定 points\-queue，BindingKey 设为order\.\#。

#### 消息生产与发送（订单服务操作）

1. 订单服务创建 “订单创建成功” 消息，指定RoutingKey=order\.create（标记这是 “订单创建” 类型消息）；

2. 通过 Channel 将消息发送到目标交换机order\-exchange。

#### 消息路由（交换机操作）

1. order\-exchange（Topic 类型）接收消息后，提取 RoutingKey=order\.create；

2. 对比自身的 Binding 规则：两个队列的 BindingKey 都是order\.\#，order\.create能匹配上；

3. 交换机将消息转发到logistics\-queue和points\-queue两个队列。

#### 消息存储与消费（队列 \+ 消费者操作）

1. 两个队列分别接收消息，按 FIFO 顺序暂存（若消息需持久化，则存储到磁盘，避免 Broker 宕机丢失）；

2. 物流服务通过 Channel 监听logistics\-queue，积分服务监听points\-queue，各自从队列中获取消息；

3. 消费者处理完业务逻辑（如创建物流单、增加用户积分）后，向 Broker 发送ACK 确认（告知 “消息已处理，可删除”）；

4. Broker 收到 ACK 后，从队列中删除该消息；若消费者未发送 ACK 就宕机，Broker 会将消息重新放入队列，等待其他消费者处理。

**总结：生产者发消息（带 RoutingKey）→ 交换机按规则路由 → 队列存储消息 → 消费者取消息 \+ ACK 确认**

## 2\.交换机 \(Exchange\) 有哪些类型

### 1\.Direct Exchange（直连交换机）

**路由规则**：**精确匹配** \- 消息的RoutingKey必须与队列绑定的BindingKey完全一致，才会被路由到该队列

**适用场景**：一对一消息路由，如 "订单 ID=123" 的消息只发送给处理该订单的消费者

### 2\.Fanout Exchange（扇出交换机）

**路由规则**：**广播模式** \- 忽略RoutingKey，将消息**无条件转发给所有绑定的队列**

**适用场景**：

全局通知（如缓存刷新、系统广播）

多服务监听（如订单创建后，同时通知物流、积分、统计服务）

### 3\.Topic Exchange（主题交换机）

**路由规则**：**通配符匹配** \- 使用\.分隔的多层级路由键，支持：

\*：匹配**一个**单词（如order\.\*匹配order\.create）

\#：匹配**零个或多个**单词（如order\.\#匹配order\.create、order\.pay\.success）

**适用场景**：

按业务主题分发（如订单、支付、物流相关消息）

灵活的订阅 \- 发布模式（如只接收 "订单创建" 或 "支付成功" 的特定类型消息）

### 4\.Headers Exchange（头交换机）

**路由规则**：**消息头匹配** \- 忽略RoutingKey，根据**消息头部属性**（Headers）匹配

**特点**：

可实现比 Topic 更复杂的匹配逻辑（支持多个键值对组合）

性能相对较低，实际应用较少

**适用场景**：需要基于消息属性（而非路由键）进行路由的特殊场景

![image.png](/img/posts/interview/rabbitmq/image%201.png)

### 总结

RabbitMQ 的四种核心交换机类型各有专长：**Direct**适合精准路由，**Fanout**用于广播，**Topic**提供灵活的主题订阅，**Headers**支持复杂属性匹配。实际应用中，**Direct**和**Topic**最为常用，而**Fanout**适用于需要 "一对多" 通知的场景，**Headers**则用于特殊的自定义路由需求。

## 3\.RabbitMQ中有哪些消息模型?

### 1\. 简单模式（Simple Model）—— 一对一

一个生产者、一个消费者、一个队列，消息直接从生产者发送到队列，消费者从队列取消息，**无交换机参与**（隐式使用默认交换机）。

### 2\.工作队列模式（Work Queue Model）—— 一对多（任务分发）

一个生产者、**多个消费者**、一个队列，消息被发送到队列后，**多个消费者竞争消费**（同一消息只会被一个消费者处理），实现 “任务负载均衡”。默认采用「轮询分发」（消息依次分给每个消费者），也可通过 basicQos 实现 “能者多劳”（消费者处理完一个再拿下一个）。

### 3\.发布 / 订阅模式（Publish/Subscribe Model）—— 广播

一个生产者、多个消费者、**一个 Fanout 交换机 \+ 多个队列**，生产者发送消息到 Fanout 交换机，交换机将消息「广播到所有绑定的队列」，每个队列的消费者都能拿到全量消息。

### 4\.路由模式（Routing Model）—— 精准匹配

一个生产者、多个消费者、**一个 Direct 交换机 \+ 多个队列**，队列与交换机绑定时有「BindingKey」，生产者发送消息时指定「RoutingKey」，交换机只将消息转发给「BindingKey 与 RoutingKey 完全一致」的队列。

### 5\.主题模式（Topic Model）—— 通配符匹配

一个生产者、多个消费者、**一个 Topic 交换机 \+ 多个队列**，是 “路由模式的增强版”——BindingKey 和 RoutingKey 支持「通配符匹配」，灵活性更高。

### 6\.RPC 模式（RPC Model）—— 请求响应

前面 5 种都是「异步消息」（生产者发完就走，不等待响应），RPC 模式是「同步请求 \- 响应」—— 生产者（客户端）发送 “请求消息”，消费者（服务端）处理后返回 “响应消息”，生产者等待并接收响应。

核心是 “请求队列 \+ 响应队列”：客户端发请求时，会指定「响应队列名」和「唯一请求 ID」，服务端处理完后，将响应消息发送到响应队列，客户端根据请求 ID 匹配响应。

## 4\.RabbitMQ如何确保消息的可靠性?

### 1\.生产者端：确保消息成功发送到 Broker

确保消息成功到达 **交换机（Exchange）** —— 生产者发送消息后，Broker 会给生产者返回「确认应答」，告知消息是否成功投递到交换机。

确保消息从 **交换机成功路由到队列** —— 如果消息到达交换机，但因 “路由键不匹配、队列不存在” 等原因无法路由，Broker 会将消息退回给生产者。

生产者重试时可能导致消息重复，需在发送端做幂等控制：

给每条消息生成唯一 ID（如 UUID），存入 Redis；

发送前先查 Redis，若消息已存在则不重复发送；

收到 Broker 确认后，删除 Redis 中的消息 ID。

### 2\.Broker 端：确保消息在 Broker 中不丢失

Broker（RabbitMQ 服务器）是消息中转站，要避免 “消息到达 Broker 后，因 Broker 宕机、队列消失导致消息丢失”，核心靠「持久化」和「高可用」。

默认情况下，消息、交换机、队列都是 “内存存储”，Broker 重启后数据丢失。需手动开启「持久化」，将数据写入磁盘。

避免单 Broker 节点宕机导致消息丢失，需部署 RabbitMQ 集群，并开启「镜像队列」

### 3\.消费者端：确保消息成功消费且不重复消费

消费者是消息终点，要避免 “消息没处理完就丢了”“重复处理消息导致业务异常”，核心靠「ACK 机制」「重试机制」「幂等性控制」。

#### 手动 ACK（确认消费）机制

默认是「自动 ACK」—— 消费者拿到消息就自动确认，若消费者处理消息时宕机（如业务没执行完），消息会丢失。需开启「手动 ACK」，由业务逻辑控制确认时机。

#### 失败重试与死信队列（DLX）

避免 “消息处理失败后一直重新入队，导致队列阻塞”—— 通过「重试机制」控制重试次数，超过次数则将消息转入「死信队列」（延迟队列的一种，专门存失败消息），后续人工处理或定时重试。

#### 消费端幂等性控制

即使前面机制都做好，仍可能因 “网络重试、Broker 重试” 导致消息重复消费（如消费者确认后，Broker 没收到确认，再次发送消息），需在消费端做幂等控制 —— 确保 “重复消费 = 一次消费的效果”。常用方案（和接口幂等性一致）：

**基于唯一消息 ID**：生产者给每条消息加唯一 ID（如 `msgId`），消费者消费前先查 Redis，若 `msgId` 已存在则直接返回成功，否则执行业务并记录 `msgId`；

**基于业务唯一键**：如订单消息用「订单号」作为唯一键，消费时先查订单状态，若已处理则直接返回；

**基于数据库唯一约束**：如插入订单记录时，用订单号做唯一索引，重复消费时会报唯一约束异常，捕获异常后返回成功。

### 总结

生产者确认（Confirm\+Returns） → Broker 持久化\+集群高可用 → 消费者手动 ACK\+重试\+死信队列\+幂等性

## 5\.RabbitMQ如何保证消息的幂等性?

### 1\.消息唯一 ID \+ Redis / 数据库去重（首选）

1\.生产者发送消息时，生成全局唯一 ID（如 UUID、雪花 ID），放入消息的「属性字段」（如 messageId 或 correlationId）；

2\.消费者接收消息后，先提取该唯一 ID；

3\.用 Redis / 数据库校验该 ID 是否已存在（原子操作，避免并发问题）：

若存在：说明已消费过，直接返回 ACK 确认；

若不存在：执行业务逻辑，成功后将该 ID 存入 Redis / 数据库（标记为已处理），再返回 ACK。

### 2\.业务唯一键去重（无需额外生成消息 ID）

如果消息本身关联了「业务天然唯一的字段」（如订单号、支付流水号），可以直接用该字段作为去重标识，无需额外生成消息 ID—— 更贴合业务，减少冗余。

### 3\.基于消息属性「MessageId/CorrelationId」去重

RabbitMQ 的消息本身支持 messageId 和 correlationId 字段，可直接复用这两个字段存储唯一标识，无需自定义消息体字段 —— 减少代码侵入。

## 6\.什么是死信队列?消息是如何成为死信的?

### 1\.什么是死信队列

死信队列（Dead\-Letter Queue，DLQ）是 RabbitMQ 中专门用于**存储 “无法被正常消费的消息”（即 “死信”）** 的队列 —— 它不是 RabbitMQ 自带的特殊队列，而是开发者手动创建的 “普通队列”，只是被指定为 “接收死信” 的目标队列。

要使用死信队列，需要配合「死信交换机（Dead\-Letter Exchange，DLX）」：

死信交换机：专门接收 “死信” 的交换机（本质是普通交换机，如 Direct/Topic 类型）；

绑定关系：给 “业务队列”（产生死信的队列）配置参数，指定其死信要转发到的「死信交换机」，再将死信交换机与「死信队列」绑定；

核心作用：避免死信被直接丢弃，方便后续排查问题（为什么消费失败）、人工处理或定时重试，保证消息不丢失。

### 2\.消息如何成为死信队列

#### 1\. 消息被消费者拒绝（Reject/Nack）且不重新入队

消费者手动 ACK 时，明确拒绝消费该消息，且设置 “不重新入队”（requeue=false）

#### 2\.消息过期（TTL 到期）

TTL（Time To Live）指消息的 “存活时间”—— 消息在队列中超过设置的 TTL 后，仍未被消费者消费，会自动变为死信。

#### 3\. 业务队列达到最大长度（队列满了）

给业务队列设置「最大长度」（最多能存储的消息数量），当队列中的消息数达到最大值后，再进入队列的新消息会直接变为死信（或队列中最早的消息被挤为死信，取决于配置）。

#### 4\.消息消费超时（RabbitMQ 延迟确认机制）

部分场景下，消费者获取消息后，因业务阻塞、宕机等原因，超过「消费超时时间」仍未返回 ACK 确认，RabbitMQ 会将该消息标记为死信，转发到死信队列。

## 7\.什么是延迟队列?RabbitMQ 如何实现延迟队列?

### 1\.什么是延迟队列?

延迟队列是一种「消息发送后不立即被消费，而是延迟指定时间后才被消费者处理」的消息队列。核心特点是 **“时间触发”** —— 消息携带 “延迟时间”，队列按时间排序，只有到达延迟时间的消息才会被投递到消费者。

### 2\.RabbitMQ 如何实现延迟队列?

#### 1\.利用「消息过期（TTL）」和「死信队列（DLQ）」的联动：

1\.消息发送到「业务队列」，该队列设置 **TTL（消息存活时间）**，且不设置消费者（消息会在队列中 “等待” 过期）；

2\.消息在业务队列中等待 TTL 到期后，变为「死信」；

3\.业务队列绑定「死信交换机」，死信会被自动转发到「死信队列」（此队列即 “延迟队列”）；

4\.消费者监听「死信队列」，接收并处理已到期的死信（即延迟处理的消息）。

- 优点：无需安装插件，RabbitMQ 原生支持，部署简单；

- 缺点：① 消息堆积时 TTL 不准确（RabbitMQ 仅对队列头部消息做过期检测，堆积时后面的消息过期后不会立即变为死信）；② 一个业务队列只能对应一个 TTL（无法给单个消息设不同延迟时间）。

#### 2\.基于延迟交换机插件（推荐，灵活高效）

这是 RabbitMQ 实现延迟队列的**最优方案**—— 通过官方插件 rabbitmq\-delayed\-message\-exchange 实现，支持给单个消息设不同延迟时间，且延迟准确，无消息堆积问题。

1\.延迟交换机（类型 x\-delayed\-message）接收消息后，不会立即转发，而是根据消息的「延迟时间」（x\-delay 参数）存储在内存中；

2\.到达延迟时间后，交换机将消息转发到绑定的「目标队列」；

3\.消费者监听目标队列，接收并处理已到期的消息。

- 优点：① 灵活（单个消息可设不同延迟时间）；② 延迟准确（无消息堆积导致的过期延迟）；③ 支持 Topic/Direct 等路由类型；

- 缺点：需要安装插件（部署时多一步操作）。

## 8\.如何解决RabbitMQ的消息堆积问题?

### 1\.快速削减已堆积的消息

#### 1\.临时扩容消费端（最直接有效）

核心逻辑：**增加消费者实例数量**，提高消费并行度，快速分摊消费压力。

#### 2\. 分流堆积消息（堆积量极大时）

操作步骤：

1. 新建 1 个「临时交换机」（如temp\.exchange）和多个「临时队列」（如temp\.queue1、temp\.queue2），绑定关系与原队列一致；

2. 暂停原生产者（避免新消息持续进入原队列，加重堆积）；

3. 用 RabbitMQ 的「Shovel/Federation 插件」或「手动编写脚本」，将原队列的堆积消息批量迁移到多个临时队列；

4. 启动多个消费者组，分别监听临时队列，并行消费（相当于 “分桶处理”）；

5. 消费完成后，恢复原生产者，删除临时组件。

#### 3\.降级非核心消费逻辑（临时提速）

若消费端有非核心业务逻辑（如日志打印、数据统计、非实时通知），临时关闭这些逻辑，只保留核心流程（如订单支付、库存扣减），提升单条消息处理速度。

### 2\.从根源避免消息堆积

#### 1\.生产者限流（避免突发流量压垮队列\)

若为高并发场景（如秒杀），在生产者前加限流组件（如 Sentinel），限制每秒发送消息数（如 1000 条 / 秒），与消费端处理能力匹配。

#### 2\. 批量发送消息（减少网络开销）

生产者单次发送 1 条消息会产生 1 次网络请求，批量发送可减少网络往返次数，提升发送效率，同时避免频繁触发 Broker 限流。

#### 3\. 优化消息大小（避免大消息阻塞）

拆分大消息：将 1 条大消息拆分为多条小消息（如将 10MB 的文件数据拆分为 100 条 100KB 的消息）；

压缩消息：生产者对消息体压缩（如 Gzip），消费端解压后处理；

避免传输大文件：大文件（如图片、视频）先存 OSS，消息中只携带文件 URL，消费端按需下载。

#### 4\.提高消费并行度

方案 1：多队列分片（避免单队列堆积）：将原单个队列（如order\.queue）拆分为多个分片队列（如order\.queue\.1、order\.queue\.2、order\.queue\.3），每个队列绑定同一个交换机，生产者通过「轮询 / 哈希」策略将消息分发到不同分片队列，每个队列对应独立的消费者组。

示例：订单消息按用户 ID 哈希分发到 3 个分片队列，3 组消费者并行处理，消费能力提升 3 倍。

方案 2：消费者线程池优化：消费端用线程池异步处理业务逻辑（消息接收后放入线程池，快速返回 ACK，避免阻塞消费线程）。

#### 5\.优化消费逻辑（提升单条消息处理速度）

避免同步阻塞：消费端不做同步 HTTP 调用、数据库慢查询（如单次查询超过 500ms），改为异步调用（如 Feign 异步、消息通知）；

数据库优化：高频查询加索引，批量操作（如批量插入 / 更新）替代单条操作，避免数据库成为瓶颈；

缓存热点数据：将高频访问的配置、用户信息存入 Redis，减少数据库查询次数。

#### 6\. 确保消费可靠性（避免重复消费 / 消费失败导致堆积）

幂等性控制,合理配置重试机制,死信队列兜底

## 9\.RabbitMQ的集群方案有哪些?

### 1\. 普通集群（Standard Cluster）—— 同机房基础集群

基于 Erlang 分布式特性实现的 “元数据共享集群”：多个 RabbitMQ 节点组成集群，**仅共享交换机、队列、绑定等 “元数据”（配置信息），不共享队列的消息数据**—— 队列的消息只存储在创建该队列的节点（称为 “队列主节点”），其他节点仅保存队列的路由信息（知道队列在哪个节点）。

优点：部署简单（无需额外插件）、无数据同步开销、适合高吞吐量场景；

缺点：队列数据单点存储（主节点宕机消息丢失）、无法分担队列的消费压力。

### 2\.镜像集群（Mirror Queue Cluster）—— 同机房高可用集群

普通集群的 “高可用增强版”：在普通集群基础上，通过「镜像队列策略」将队列的消息同步到集群中多个节点（称为 “镜像节点”）—— 队列主节点存储消息，镜像节点实时同步消息，主节点宕机后，镜像节点自动切换为主节点，消息不丢失。

优点：队列高可用（主节点宕机镜像节点接管）、消息不丢失（持久化 \+ 镜像同步）、对业务透明（无需修改代码）；

缺点：数据同步有性能开销（节点越多开销越大）、集群吞吐量略低于普通集群、不支持跨地域部署（网络延迟会导致同步超时）。

### 3\.异地多活集群（Federation/Shovel）—— 跨地域高可用

针对 “跨机房 / 跨地域” 场景设计的集群方案：通过「Federation 插件」或「Shovel 插件」，实现不同地域集群（如北京集群、上海集群）间的消息同步 / 路由，解决普通集群 / 镜像集群无法跨地域部署的问题（跨地域网络延迟高，数据同步会超时）。

优点：支持跨地域部署（容忍高网络延迟）、两地集群独立运行（单地域集群故障不影响另一地域）、灵活配置（可单向 / 双向同步）；

缺点：消息有同步延迟（跨地域网络延迟导致）、需安装额外插件、配置较复杂（需维护联邦连接 / Shovel 通道）。

### 4\.仲裁队列（Quorum Queue）

仲裁队列是RabbitMQ官方支持的新一代高可用队列，内部采用Raft算法实现，队列副本也会分leader角色和follow角色，只要一半以上节点可用集群即可用，其在高可用和性能之间做了很好的平衡。

![image.png](/img/posts/interview/rabbitmq/image%203.png)

优点:

相比于镜像队列，仲裁队列在一致性算法上做了升级，换成了raft算法，节点同步的容错能力明显增强：只需要一半以上的节点完成同步确认即可认为成功。

相比于镜像队列需要全量同步情况，仲裁也做了优化：支持增量同步，并且同步过程中并不会导致整个集群不可用。

相比于镜像队里，不存在队列副本之间的分区问题。

缺点:

低于3\.8的版本中不支持仲裁队列

要求集群节点为奇数，部分特性，如优先级不支持，部分特性如ttl，长度限制需要3\.10版本支持。

## 1\.介绍一下Redis的常用数据结构

1. String\(字符串\):普通的key,value,用于存储最简单的键值对

2. List\(列表\):有序集合，可以用作消息队列，元素可以重复

3. Set\(无序集合类型\):无序集合,去重，支持交并查集。

4. ZSet\(有序集合类型\):有序，带权重\(分数\)，支持按分数排序\.实现排行榜等功能。

5. Hash\(哈希表类型\):适合存储对象类型的数据。

## 2\.介绍Redis的持久化机制

Redis有三种持久化方式:

1\.快照（snapshotting，RDB）

2\.只追加文件（append\-only file, AOF）

3\.RDB 和 AOF 的混合持久化\(Redis 4\.0 新增\)

### RDB持久化

Redis 可以通过创建快照来获得存储在内存里面的数据在 **某个时间点** 上的副本。Redis 创建快照之后，可以对快照进行备份，可以将快照复制到其他服务器从而创建具有相同数据的服务器副本（Redis 主从结构，主要用来提高 Redis 性能），还可以将快照留在原地以便重启服务器的时候使用。

**RDB 创建快照时会阻塞主线程吗？**

Redis 提供了两个命令来生成 RDB 快照文件：

save:同步保存操作，会阻塞 Redis 主线程；

bgsave:fork 出一个子进程，子进程执行，不会阻塞 Redis 主线程，默认选项;

### AOF持久化

与快照持久化相比，AOF 持久化的实时性更好。默认情况下 Redis 没有开启 AOF（append only file）方式的持久化（Redis 6\.0 之后已经默认是开启了）。

开启 AOF 持久化后每执行一条会更改 Redis 中的数据的命令，Redis 就会将该命令写入到 AOF 缓冲区 server\.aof_buf 中，然后再写入到 AOF 文件中（此时还在系统内核缓存区未同步到磁盘），最后再根据持久化方式（ fsync策略）的配置来决定何时将系统内核缓存区的数据同步到硬盘中的。

AOF工作流程如下:

![image.png](/img/posts/interview/redis/image%203.png)

**AOF 持久化方式有哪些？**

appendfsync always：主线程调用 write 执行写操作后，后台线程（ aof_fsync 线程）立即会调用 fsync 函数同步 AOF 文件（刷盘），fsync 完成后线程返回，这样会严重降低 Redis 的性能（write \+ fsync）。

appendfsync everysec：主线程调用 write 执行写操作后立即返回，由后台线程（ aof_fsync 线程）每秒钟调用 fsync 函数（系统调用）同步一次 AOF 文件（write\+fsync，fsync间隔为 1 秒）。

appendfsync no：主线程调用 write 执行写操作后立即返回，让操作系统决定何时进行同步，Linux 下一般为 30 秒一次（write但不fsync，fsync 的时机由操作系统决定）。

### 如何选择 RDB 和 AOF？

**RDB 比 AOF 优秀的地方：**

RDB 文件存储的内容是经过压缩的二进制数据， 保存着某个时间点的数据集，文件很小，适合做数据的备份，灾难恢复。AOF 文件存储的是每一次写命令，类似于 MySQL 的 binlog 日志，通常会比 RDB 文件大很多。当 AOF 变得太大时，Redis 能够在后台自动重写 AOF。新的 AOF 文件和原有的 AOF 文件所保存的数据库状态一样，但体积更小。不过， Redis 7\.0 版本之前，如果在重写期间有写入命令，AOF 可能会使用大量内存，重写期间到达的所有写入命令都会写入磁盘两次。

使用 RDB 文件恢复数据，直接解析还原数据即可，不需要一条一条地执行命令，速度非常快。而 AOF 则需要依次执行每个写命令，速度非常慢。也就是说，与 AOF 相比，恢复大数据集的时候，RDB 速度更快。

**AOF 比 RDB 优秀的地方**：

RDB 的数据安全性不如 AOF，没有办法实时或者秒级持久化数据。生成 RDB 文件的过程是比较繁重的， 虽然 BGSAVE 子进程写入 RDB 文件的工作不会阻塞主线程，但会对机器的 CPU 资源和内存资源产生影响，严重的情况下甚至会直接把 Redis 服务干宕机。AOF 支持秒级数据丢失（取决 fsync 策略，如果是 everysec，最多丢失 1 秒的数据），仅仅是追加命令到 AOF 文件，操作轻量。

RDB 文件是以特定的二进制格式保存的，并且在 Redis 版本演进中有多个版本的 RDB，所以存在老版本的 Redis 服务不兼容新版本的 RDB 格式的问题。

AOF 以一种易于理解和解析的格式包含所有操作的日志。你可以轻松地导出 AOF 文件进行分析，你也可以直接操作 AOF 文件来解决一些问题。比如，如果执行`FLUSHALL`命令意外地刷新了所有内容后，只要 AOF 文件没有被重写，删除最新命令并重启即可恢复之前的状态。

综上:

Redis 保存的数据丢失一些也没什么影响的话，可以选择使用 RDB。

不建议单独使用 AOF，因为时不时地创建一个 RDB 快照可以进行数据库备份、更快的重启以及解决 AOF 引擎错误。

如果保存的数据要求安全性比较高的话，建议同时开启 RDB 和 AOF 持久化或者开启 RDB 和 AOF 混合持久化。

## 3\.Redis的数据如何和mysql进行同步?

### 1\.Cache Aside Pattern\(旁路缓存模式\)

在大部分业务系统中，Redis 作为缓存层用于提升系统的读取性能，而 MySQL 作为持久化存储，用于保证数据的可靠性。最常见的场景是：

系统先查询 Redis 缓存，如果缓存中没有数据，再从 MySQL 中查询并将数据写入 Redis 缓存。

更新数据时，更新 MySQL 并删除 Redis 缓存，使缓存数据失效，保证下次读取时能拿到最新数据。

**保持一致性的策略:**

1\.缓存淘汰策略:MySQL 数据更新后立即删除 Redis 缓存，确保下次读取时能获取到最新数据。即通过 "删除缓存" 的方式避免脏数据存在于缓存中。

2、并发问题：当并发请求较高时，可能会出现“缓存雪崩”或“缓存击穿”问题。例如：A 更新 MySQL 数据，B 在缓存失效的瞬间读取了旧数据，再次缓存到 Redis。为解决此问题，可以采用 延迟双删策略：

删除 Redis 缓存。

更新 MySQL。

适当延迟（如 500ms），再次删除 Redis 缓存，确保在并发情况下不存在缓存不一致问题。

### 2\.先更新缓存再更新数据库

在某些实时性要求较高的场景\(例如秒杀业务\)中，可以考虑先更新 Redis 缓存，然后再异步更新 MySQL 数据库。

**数据最终一致性**：Redis 作为前端实时数据的缓存，MySQL 作为后端数据的持久化存储，采用异步更新策略时，一致性无法保证是**强一致性**，但可以通过使用**消息队列**等手段来保证**最终一致性**。异步写入 MySQL 时，如果操作失败，可以通过重试机制或补偿机制恢复一致性。

### 3\.双写操作

有时业务需要同时更新 Redis 和 MySQL 的数据，如用户余额更新、积分奖励系统等场景中，Redis 和 MySQL 需要同步写入。

一致性:

如果同时写 Redis 和 MySQL，可能会面临一致性问题。常见解决方案是通过**事务补偿机制**来实现。具体步骤：

1）使用数据库事务保证 MySQL 写入成功。

2）如果 Redis 写入失败，可以尝试重试，或在事务结束后通过补偿机制将失败的数据写入 Redis。

### 4\.数据回写（Write Back）策略

数据回写模式适用于 Redis 作为缓存层，MySQL 作为持久化存储层，但 Redis 中数据修改后并不立即同步更新 MySQL，而是在特定时机触发数据回写。

如何保障一致性：**持久化与批量同步**：通过 Redis 的持久化机制（如 RDB、AOF），在 Redis 崩溃时不会丢失数据。通过定时器或事件驱动系统触发批量同步 MySQL。

## 4\.缓存穿透,雪崩,击穿的概念以及解决方案。

### 1\.缓存穿透

概念:缓存穿透是指**缓存和数据库中都没有的数据**，而用户不断发起请求。由于缓存是不命中时被动写的，并且出于容错考虑，如果从存储层查不到数据则不写入缓存，这将导致这个不存在的数据每次请求都要到存储层去查询，失去了缓存的意义。

解决方案:可以给这个查不到的数据写入redis进行缓存成null，并设置一个较短的过期时间，防止多次查询数据库

### 2\.缓存击穿

概念:缓存击穿是指缓存中没有但数据库中有的数据（一般是缓存时间到期），这时由于并发用户特别多，同时读缓存没读到数据，又同时去数据库去取数据，引起数据库压力瞬间增大，造成过大压力

解决方案:

1\.设置热点数据永远不过期。

2\.**接口限流与熔断，降级。**重要的接口一定要做好限流策略，防止用户恶意刷接口，同时要降级准备，当接口中的某些 服务 不可用时候，进行熔断，失败快速返回机制。

3\.**布隆过滤器。**bloomfilter就类似于一个hash set，用于快速判某个元素是否存在于集合中，其典型的应用场景就是快速判断一个key是否存在于某容器，不存在就直接返回。布隆过滤器的关键就在于hash算法和容器大小，

4\.加互斥锁。

### 3\.缓存雪崩

概念:缓存雪崩是指缓存中数据大批量到过期时间，而查询数据量巨大，引起数据库压力过大甚至宕机。和缓存击穿不同的是，缓存击穿指并发查同一条数据，缓存雪崩是不同数据都过期了，很多数据都查不到从而查数据库。

解决方案:

1\.缓存数据的过期时间设置随机，防止同一时间大量数据过期现象发生。

2\.如果缓存数据库是分布式部署，将热点数据均匀分布在不同搞得缓存数据库中。

3\.设置热点数据永远不过期。

## 5\.Redis如何判断一个KEY是否过期?

Redis 判断一个 Key 是否过期，核心依赖于**过期字典（expires dictionary）** 存储的过期时间，结合**当前服务器时间**进行比对，同时配合特定的删除策略确保过期键能被及时处理。具体机制如下：

Redis 的每个数据库（redisDb 结构）中，都维护了一个**过期字典（expires）**，专门用于存储所有设置了过期时间的 Key 及其对应的过期时间。

**键（key）**：指向数据库中实际 Key 的指针（如字符串、哈希等数据结构的键）

**值（value）**：该 Key 的过期时间

例如，当执行 SET key value EX 10（设置 Key 10 秒后过期）时，Redis 会：

1. 在数据库中创建 key 及其值 value；

2. 在 expires 字典中添加一条记录：key → 当前时间戳 \+ 10000 毫秒。

**当需要判断一个 Key 是否过期时，Redis 会执行以下步骤：**

**检查该 Key 是否在过期字典中**：

若不在 `expires` 字典中：说明该 Key 未设置过期时间，**不过期**。

若在 `expires` 字典中：获取其存储的过期时间戳（`expire_time`）。

**对比过期时间与当前服务器时间**：

若 `当前服务器时间 > expire_time`：该 Key **已过期**。

若 `当前服务器时间 ≤ expire_time`：该 Key **未过期**。

## 6\.过期键的删除策略

1\.惰性删除（Lazy Expiration）

**触发时机**：当客户端访问某个 Key 时（如 `GET key`），Redis 会先判断该 Key 是否过期。

**处理逻辑**：

若已过期：立即从数据库和 `expires` 字典中删除该 Key，返回空结果（仿佛 Key 不存在）。

若未过期：正常返回 Key 的值。

**优点**：只在访问时处理，不消耗额外资源，对性能影响小。

**缺点**：若过期 Key 长期未被访问，会一直占用内存（可能导致内存泄漏）。

2\.定期删除（Periodic Expiration）

**触发时机**：Redis 服务器每隔一段时间（默认每 100 毫秒，可通过 `hz` 配置调整）主动执行一次过期键扫描。

**处理逻辑**：

1. 从 `expires` 字典中随机抽取部分 Key（默认每次抽 20 个）。

2. 检查这些 Key 是否过期，删除已过期的 Key。

3. 若本次扫描中过期 Key 的比例超过 25%，则重复步骤 1（避免大量过期 Key 堆积），否则结束本轮扫描。

**优点**：主动清理部分过期 Key，减少内存浪费。

**缺点**：扫描频率和范围需平衡（太频繁影响性能，太稀疏则内存占用高）。

3\.内存淘汰机制（Memory Eviction）

当 Redis 内存使用达到 `maxmemory` 限制时，会触发内存淘汰策略（如 `allkeys-lru`、`volatile-lru` 等），此时会优先删除**已过期的 Key**（若策略允许），释放内存。

这是一种 “被动兜底” 机制，确保内存不超限，间接配合过期键的清理。

## 7\.Redis内存淘汰策略有哪些

如果Redis服务器打开了`maxmemory`选项，并且服务器占用的内存数超过了`maxmemory`选项所设置的上限值时，会进行内存淘汰，常见的淘汰策略如下：

1\.no\-envicition：

该策略对于写请求不再提供服务，会直接返回错误，当然排除del等特殊操作，redis默认是no\-envicition策略。

2\.allkeys\-random：

从redis中随机选取key进行淘汰

3\.allkeys\-lru：

使用LRU（Least Recently Used，最近最少使用）算法，从redis中选取使用最少的key进行淘汰

4\.volatile\-random：

从redis中设置过过期时间的key，进行随机淘汰

5\.volatile\-ttl：

从redis中选取即将过期的key，进行淘汰

6\.volatile\-lru：

使用LRU（Least Recently Used，最近最少使用）算法，从redis中设置过过期时间的key中，选取最少使用的进行淘汰

7\.volatile\-lfu:

使用LFU（Least Frequently Used，最不经常使用），从设置了过期时间的键中选择某段时间之内使用频次最小的键值对清除掉

8\.allkeys\-lfu:

使用LFU（Least Frequently Used，最不经常使用），从所有的键中选择某段时间之内使用频次最少的键值对清除

## 9\.主从复制的概念以及数据同步的流程

主从复制模式中包含一个主[数据库](https://cloud.tencent.com/product/tencentdb-catalog?from_column=20065&from=20065)实例（master）与一个或多个从数据库实例（slave），如下图

![image.png](/img/posts/interview/redis/image.png)

客户端可对主数据库进行读写操作，对从数据库进行读操作，主数据库写入的数据会实时自动同步给从数据库。

具体工作机制为：

1. slave启动后，向master发送SYNC命令，master接收到SYNC命令后通过bgsave保存快照（即上文所介绍的RDB持久化），并使用缓冲区记录保存快照这段时间内执行的写命令

2. master将保存的快照文件发送给slave，并继续记录执行的写命令

3. slave接收到快照文件后，加载快照文件，载入数据

4. master快照发送完后开始向slave发送缓冲区的写命令，slave接收命令并执行，完成复制初始化

5. 此后master每次执行一个写命令都会同步发送给slave，保持master与slave之间数据的一致性

## 10\.什么是哨兵模式，哨兵模式的工作原理

1\. 基本原理:哨兵模式基于主从复制模式，只是引入了哨兵来监控与自动处理故障。如图

![image.png](/img/posts/interview/redis/image%201.png)

哨兵顾名思义，就是来为Redis集群站哨的，一旦发现问题能做出相应的应对处理。其功能包括

1. 监控master、slave是否正常运行

2. 当master出现故障时，能自动将一个slave转换为master（大哥挂了，选一个小弟上位）

3. 多个哨兵可以监控同一个Redis，哨兵之间也会自动监控

工作流程:

在配置文件中通过 sentinel monitor来定位master的IP、端口，一个哨兵可以监控多个master数据库，只需要提供多个该配置项即可。哨兵启动后，会与要监控的master建立两条连接：

1. 一条连接用来订阅master的\_sentinel\_:hello频道与获取其他监控该master的哨兵节点信息

2. 另一条连接定期向master发送INFO等命令获取master本身的信息

与master建立连接后，哨兵会执行三个操作：

1. 定期（一般10s一次，当master被标记为主观下线时，改为1s一次）向master和slave发送INFO命令

2. 定期向master和slave的\_sentinel\_:hello频道发送自己的信息

3. 定期（1s一次）向master、slave和其他哨兵发送PING命令

发送INFO命令可以获取当前数据库的相关信息从而实现新节点的自动发现。所以说哨兵只需要配置master数据库信息就可以自动发现其slave信息。获取到slave信息后，哨兵也会与slave建立两条连接执行监控。通过INFO命令，哨兵可以获取主从数据库的最新信息，并进行相应的操作，比如角色变更等。

接下来哨兵向主从数据库的sentinel:hello频道发送信息与同样监控这些数据库的哨兵共享自己的信息，发送内容为哨兵的ip端口、运行id、配置版本、master名字、master的ip端口还有master的配置版本。这些信息有以下用处：

1. 其他哨兵可以通过该信息判断发送者是否是新发现的哨兵，如果是的话会创建一个到该哨兵的连接用于发送PING命令。

2. 其他哨兵通过该信息可以判断master的版本，如果该版本高于直接记录的版本，将会更新

3. 当实现了自动发现slave和其他哨兵节点后，哨兵就可以通过定期发送PING命令定时监控这些数据库和节点有没有停止服务。

如果被PING的数据库或者节点超时（通过 sentinel down\-after\-milliseconds master\-name milliseconds 配置）未回复，哨兵认为其主观下线（sdown，s就是Subjectively —— 主观地）。如果下线的是master，哨兵会向其它哨兵发送命令询问它们是否也认为该master主观下线，如果达到一定数目（即配置文件中的quorum）投票，哨兵会认为该master已经客观下线（odown，o就是Objectively —— 客观地），并选举领头的哨兵节点对主从系统发起故障恢复。若没有足够的sentinel进程同意master下线，master的客观下线状态会被移除，若master重新向sentinel进程发送的PING命令返回有效回复，master的主观下线状态就会被移除

哨兵认为master客观下线后，故障恢复的操作需要由选举的领头哨兵来执行，选举采用Raft算法：

1. 发现master下线的哨兵节点（我们称他为A）向每个哨兵发送命令，要求对方选自己为领头哨兵

2. 如果目标哨兵节点没有选过其他人，则会同意选举A为领头哨兵

3. 如果有超过一半的哨兵同意选举A为领头，则A当选

4. 如果有多个哨兵节点同时参选领头，此时有可能存在一轮投票无竞选者胜出，此时每个参选的节点等待一个随机时间后再次发起参选请求，进行下一轮投票竞选，直至选举出领头哨兵

选出领头哨兵后，领头者开始对系统进行故障恢复，从出现故障的master的从数据库中挑选一个来当选新的master,选择规则如下：

1. 所有在线的slave中选择优先级最高的，优先级可以通过slave\-priority配置

2. 如果有多个最高优先级的slave，则选取复制偏移量最大（即复制越完整）的当选

3. 如果以上条件都一样，选取id最小的slave

挑选出需要继任的slave后，领头哨兵向该数据库发送命令使其升格为master，然后再向其他slave发送命令接受新的master，最后更新数据。将已经停止的旧的master更新为新的master的从数据库，使其恢复服务后以slave的身份继续运行。

## 11\.什么是分片集群

![image.png](/img/posts/interview/redis/image%202.png)

Cluster采用无中心结构,它的特点如下：

1. 所有的redis节点彼此互联\(PING\-PONG机制\),内部使用二进制协议优化传输速度和带宽

2. 节点的fail是通过集群中超过半数的节点检测失效时才生效

3. 客户端与redis节点直连,不需要中间代理层\.客户端不需要连接集群所有节点,连接集群中任何一个可用节点即可

Cluster模式的具体工作机制：

1. 在Redis的每个节点上，都有一个插槽（slot），取值范围为0\-16383

2. 当我们存取key的时候，Redis会根据CRC16的算法得出一个结果，然后把结果对16384求余数，这样每个key都会对应一个编号在0\-16383之间的哈希槽，通过这个值，去找到对应的插槽所对应的节点，然后直接自动跳转到这个对应的节点上进行存取操作

3. 为了保证高可用，Cluster模式也引入主从复制模式，一个主节点对应一个或者多个从节点，当主节点宕机的时候，就会启用从节点

4. 当其它主节点ping一个主节点A时，如果半数以上的主节点与A通信超时，那么认为主节点A宕机了。如果主节点A和它的从节点都宕机了，那么该集群就无法再提供服务了

## 1\. 介绍一下微服务常用组件

1\.服务注册与发现（Service Registry \& Discovery）

2\.API网关（API Gateway）

3\.配置中心\(Configuration Center\)

4\.服务熔断与降级（Circuit Breaker \& Fallback）

5\.分布式追踪与日志（Distributed Tracing \& Logging）

## 2\.服务注册和服务发现的概念

服务注册：服务（通常叫 “服务提供者”）启动时，主动将自己的关键信息（如服务名、IP 地址、端口、接口信息等）登记到一个专门的 “**注册中心**”（比如 Nacos、Eureka 等）的过程。

服务发现：当一个服务（通常叫 “服务消费者”）需要调用其他服务时，不会直接用硬编码的地址，而是去注册中心查询目标服务的最新地址信息，再发起调用的过程。

## 3\.Eureka和Nacos都可以作为注册中心，说一下它们的区别

**核心定位不同**

Eureka：只做服务注册与发现，不碰配置管理，设计理念是 “精简专一”。

Nacos：不仅能做注册中心，还自带配置中心（比如动态改服务配置不用重启），相当于 “一站式微服务工具”，不用额外搭配置组件（比如 Spring Cloud Config）。

**架构模式（CAP 理论）不同**

Eureka：严格遵循AP 原则（可用性 \+ 分区容错性），牺牲一致性。比如集群中某个节点挂了，其他节点仍能正常提供注册 / 查询服务，不会因为同步数据卡住，适合对 “服务可用” 要求高于 “数据绝对一致” 的场景。

Nacos：支持AP 和 CP 切换（默认 AP）。想追求可用性就用 AP（和 Eureka 一样），想保证数据一致（比如金融场景）就切 CP，灵活性更高。

**服务健康检查方式不同**

Eureka：靠服务端 “心跳上报”（客户端定期发请求说自己活着），心跳停了不会立刻删服务，会有 “自我保护机制”（避免网络抖动误删健康服务）。

Nacos：支持多种健康检查 —— 心跳上报、端口探测（主动连服务端口看通不通）、HTTP 探测（调用服务接口看返回），能更快发现挂掉的服务，而且没有 “自我保护机制”（不会因为网络问题保留无效服务）。

**负载均衡与易用性不同**

Eureka：本身不提供负载均衡逻辑，需要搭配 Ribbon（Spring Cloud 的负载均衡组件）才能实现 “根据服务名选实例调用”。

Nacos：自带负载均衡功能，不用额外装 Ribbon，直接通过服务名调用就能自动做负载均衡，配置起来更简单。

**生态与兼容性不同**

Eureka：主要适配Spring Cloud 生态，和 Spring Cloud 组件（Feign、Ribbon 等）无缝衔接，但不支持 Dubbo、gRPC 等非 Spring Cloud 框架。

Nacos：兼容性更强 —— 既支持 Spring Cloud，也支持 Dubbo、gRPC，还能对接 K8s，适合混合架构（比如既有 Spring Cloud 服务，又有 Dubbo 服务）。

**现状与维护不同**

Eureka：Netflix 已经停止维护（2\.x 版本后不更新），虽然还能用，但没有新功能和 bug 修复，长期用有风险。

Nacos：阿里开源的，一直在活跃维护，新功能（比如服务网格、流量控制）不断更，生态越来越完善，生产环境用起来更有保障。

## 4\.项目中服务远程调用时的负载均衡是如何实现的?

服务远程调用的负载均衡，核心是**从注册中心获取目标服务的多个实例列表，再通过指定算法挑选一个实例发起调用**，避免单个实例压力过大。常见实现分 “客户端负载均衡” 和 “服务端负载均衡” 两类

## 5\.介绍\-下Ribbon中常用的负载均衡策略

**轮询（Round Robin）**：按顺序依次选择服务实例，实现请求的均匀分布。

**随机（Random）**：随机选择一个服务实例，适用于对请求分布无特殊要求的场景。

**响应时间加权（Response Time Weighted）**：根据服务实例的响应时间动态调整权重，响应时间短的实例被选中的概率更高。

**区域感知（Zone Aware）**：优先选择与客户端在同一区域的服务实例，减少跨区域网络延迟。

## 6\.什么是服务雪崩，以及服务雪崩的解决方案

服务雪崩:服务雪崩是**微服务链路中故障扩散导致的 “连锁瘫痪” 现象**—— 当链路中某个核心服务（比如支付服务）因宕机、网络故障等原因不可用，依赖它的上游服务（比如下单服务）会因 “请求超时等待”“重试” 导致资源耗尽（线程池满、连接占满），进而自身不可用；这个故障会沿着链路继续向上扩散（比如订单列表服务依赖下单服务，也会跟着不可用），最终导致整个微服务系统或核心业务链路瘫痪。

解决方案:

1\.熔断： 当某个服务的调用失败率（超时、异常）达到阈值（比如 50%），就自动 “熔断”（断开调用链路），后续请求不再发往故障服务，直接返回兜底结果，避免上游服务因等待耗尽资源

2\.降级：服务压力达到阈值（比如 CPU 使用率 90%、线程池满），主动 “降级” 非核心功能（比如商品详情页的 “浏览历史”“推荐商品”），释放资源给核心功能（比如 “商品查询”“下单”），避免核心功能瘫痪。

3\.限流: 给服务或接口设置 “流量上限”（比如每秒最多处理 1000 个请求），超过上限的请求直接拒绝或排队，避免大量请求同时涌入导致服务资源耗尽（线程、连接占满）。

4\.超时与重试:给每个远程调用设置 “超时时间”（比如 1 秒），超过时间直接返回失败，不允许线程一直阻塞等待（比如调用支付服务 1 秒没响应，就直接放弃，避免线程池被占满）。

5\.资源隔离:给不同服务的调用分配独立的资源（比如线程池、连接池），比如 “调用支付服务” 用线程池 A，“调用库存服务” 用线程池 B—— 即使支付服务故障导致线程池 A 满了，也不会影响线程池 B（调用库存服务），实现故障隔离。

## 7\.解释一下限流算法中的漏桶算法和令牌桶算法

**漏桶算法**基于固定容量的桶和恒定的流出速率来平滑处理请求，无论流入速率如何变化都能保证恒定的输出速率，具有流量平滑、后端压力稳定的优势，但同时也因此无法满足合理的突发流量需求，可能导致部分正常请求被误杀，这种方式更适合对后端服务保护要求高、流量相对稳定的场景。

![image.png](/img/posts/interview/microservices/image.png)

**令牌桶算法**通过以固定速率向桶中放入令牌，请求到达时消耗令牌来控制流量，由于桶中可以储存一定数量的令牌，这种方式支持一定程度的突发流量处理，能够在流量波动时提供更好的用户体验，允许短时间内的请求速率超过平均速率，但同时也因为允许突发流量，在极端情况下可能对后端服务造成瞬时压力，因此更适合流量波动较大、需要处理突发请求的场景。

## 8\.Spring Cloud Gateway 的路由和断言是什么关系?

**1\.路由（Route）：网关的核心转发规则**

路由是 Gateway 中最基础的组件，每个路由都定义了 “请求从哪来、到哪去”，核心包含 4 个部分：

**ID**：路由唯一标识（比如route\-order）；

**目标 URI**：请求要转发到的目标地址（可以是具体服务名，如 `lb://order-service`，lb表示负载均衡；也可以是固定 URL，如 `http://localhost:8081`）；

**断言集合（Predicate Set）**：判断请求是否匹配当前路由的条件（比如 “请求路径是 /order/\*\*”“请求方法是 GET”）；

**过滤器集合（Filter Set）**：请求转发前后的加工逻辑（比如添加请求头、限流、熔断）。

**2\. 断言（Predicate）：请求的 “匹配筛选器”**

断言是基于 Spring Framework 的 Predicate 接口实现的，本质是一个 “布尔判断逻辑”—— 输入是当前的请求对象（ServerWebExchange），输出是true或false：

若输出true：表示请求符合当前断言条件；

若输出false：表示请求不符合，路由不会生效。

Gateway 内置了很多常用断言（比如路径断言、方法断言、参数断言等），也支持自定义断言，目的就是 “精准筛选出需要走当前路由的请求”。

**两者之间的关系:**

一个路由可以配置**多个断言**（是 “与” 关系，不是 “或”），只有当请求**同时满足所有断言**时，这条路由才会被 “命中”，请求才会按照路由的规则转发到目标服务。

## 9\.Spring Cloud Gateway中常见的过滤器

**1\.全局过滤器**

**\(1\)负载均衡过滤器（LoadBalancerClientFilter）:**实现 “服务名转发” 的负载均衡（对应uri: lb://服务名），自动从注册中心拉取服务实例，按负载均衡策略挑选实例转发。

**\(2\)限流过滤（RequestRateLimiterGatewayFilterFactory）:**对所有请求做限流（防止流量冲垮网关 / 服务），支持基于 IP、用户、接口等维度限流。

**\(3\) 跨域过滤器\(CorsWebFilter\):**解决前端跨域问题（浏览器同源策略限制），全局统一配置跨域规则。

**\(4\)日志过滤器\(自定义\):**全局打印请求日志（如请求路径、方法、IP、响应时间），方便排查问题。

**2\.局部过滤器**

**\(1\) 添加请求头过滤器（AddRequestHeader）:**转发请求前，给请求添加自定义请求头（如传递网关标识、Token 等）。

**\(2\)添加响应头过滤器（AddResponseHeader）:**响应返回给前端前，给响应添加自定义响应头（如接口版本、服务名）。

**\(3\)路径重写过滤器（RewritePath）:**修改请求路径（如去掉前端请求的/api前缀，适配下游服务接口）。

**\(4\)请求参数过滤器（AddRequestParameter/RemoveRequestParameter）:**给请求添加参数，或删除不需要的参数。

**\(5\)熔断降级过滤器（CircuitBreaker）:**对当前路由做熔断降级（避免下游服务故障扩散，对应服务雪崩解决方案）。

## 10\.Sentinel中常用的流量控制规则有哪些?

**1\. 直接限流**

**原理**：直接对目标资源（如接口）设置 QPS / 并发线程数阈值，超过阈值的请求直接拒绝（返回预设提示，如 “系统繁忙，请稍后重试”）。

**2\.关联限流 **

**原理：**不直接限制当前资源，而是监控 “关联资源” 的流量 —— 当关联资源达到限流阈值时，就限制当前资源的请求。

**3\.链路限流**

**原理：**只限制 “特定调用链路” 对资源的请求，而非所有链路。通俗说：“同一个接口（如/user/get），如果是 A 接口调用的就限流，是 B 接口调用的就不限流”。

**4\. Warm Up（预热）限流 **

**原理:**限流阈值不是一开始就达到设置值，而是从 “低阈值” 逐渐升到 “目标阈值”（默认 30 秒），避免冷启动时服务被突发流量冲垮。

**5\.排队等待限流**

**原理：**超过阈值的请求不直接拒绝，而是进入队列排队，按 “固定速率” 依次处理（类似漏桶算法 “匀速出水”），避免流量波动。注意：只支持 “QPS 阈值类型”，且队列有最大等待时间（默认 500 毫秒，超过则拒绝）。

**6\.热点参数限流**

**原理:**对资源中 “热点参数”（如商品 ID、用户 ID）进行限流 —— 不是限制整个接口，而是限制 “携带特定参数” 的请求。

## 11\.什么是CAP定理?

CAP 定理是**分布式系统设计的核心权衡原则**—— 一个分布式系统（比如注册中心集群、数据库集群）中，无法同时保证「一致性（C）、可用性（A）、分区容错性（P）」这三个特性，只能优先保证其中两个。

## 12\.什么是BASE理论?

BASE 理论是**分布式系统设计中对 CAP 定理的 “柔性折中方案”** —— 它不追求 CAP 的 “三者兼得”，也不极端偏向 AP 或 CP，而是以 “基本可用、软状态、最终一致性” 为核心，容忍数据暂时不一致，换取系统高可用性，特别适合微服务、电商等对可用性要求高的场景

**1\.Basically Available（基本可用）**

系统 “核心功能能正常用”，而非 100% 可用 —— 允许在极端场景下（如大促、故障），非核心功能降级、响应慢一点，但核心流程不能崩。

**2\.Soft state（软状态）**

系统中的数据可以存在 “暂时不一致的中间状态”，不用要求所有节点数据实时同步 —— 这种中间状态是允许的，不会影响系统可用性。

**3\.Eventually consistent（最终一致性）**

虽然存在 “软状态”（暂时不一致），但在没有新数据写入的情况下，经过一段时间（如几秒、几分钟），所有节点的数据会自动达成一致 —— 不追求 “实时一致”，但要保证 “最终一致”。

## 13\.介绍一下分布式锁的常见实现方案

**1\.基于 Redis 的分布式锁（最常用，高并发首选）**

通过 Redis 的「原子命令」保证 “锁的获取 / 释放” 是原子操作，避免并发漏洞；通过「过期时间」防止死锁

**2\.基于 ZooKeeper 的分布式锁（高可靠，一致性优先）**

利用 ZooKeeper 的「临时有序节点」和「Watcher 监听机制」实现，可靠性高，天然支持公平锁。

**3\.基于数据库的分布式锁（最简单，低并发适用）**

利用数据库的「唯一约束」或「行锁」实现，不用额外部署中间件，适合并发量低、快速落地的场景。

## 14\.什么是分布式事务，分布式事务的解决方案有哪些?

分布式事务是指**跨多个服务或多个数据源的事务**—— 简单说，一个业务操作需要同时操作多个不同节点（比如不同服务的数据库、不同机房的数据库），所有操作必须 “同时成功” 或 “同时失败”，不能出现 “部分成功、部分失败” 的情况。

解决方案:

**1\.Seata 分布式事务（微服务首选，阿里开源）**

Seata 是目前微服务架构中最常用的分布式事务解决方案，支持多种模式，适配 Spring Cloud、Dubbo 等生态，无侵入或低侵入，维护活跃。

**（1）AT 模式（默认，无侵入，最常用）**

**（2）TCC 模式（高并发核心场景，侵入性强）**

**（3）SAGA 模式（长事务场景，如物流、流程调度）**

**2\.消息队列 \+ 最终一致性（非核心场景，简单易用）**

基于 BASE 理论，放弃强一致性，追求最终一致性，通过 “本地事务 \+ 消息队列” 实现，无额外中间件依赖，适合非核心业务（如订单通知、积分发放）。

**原理：“本地事务与消息发送原子性”**

步骤（以 “下单后发送积分” 为例）：

1\.订单服务执行本地事务（创建订单），同时将 “发放积分” 的消息写入**本地消息表**（和订单库在同一个数据库，靠本地事务保证 “订单创建” 和 “消息写入” 原子性）；

2\.启动定时任务，扫描本地消息表中 “未发送” 的消息，发送到消息队列（如 RabbitMQ、RocketMQ）；

3\.积分服务消费消息，执行 “发放积分” 的本地事务；

4\.若积分服务消费失败，消息队列重试（直到成功），最终保证 “订单创建” 和 “积分发放” 一致。

**3\.2PC/3PC（传统强一致性方案，几乎淘汰）**

2PC（Two\-Phase Commit，两阶段提交）是传统分布式事务的强一致性方案，分为 “准备阶段” 和 “提交阶段”，但可用性极差，现在很少用。

**4\.TCC 纯手写（极致性能场景，极少用）**

不依赖 Seata 等组件，纯手写 Try/Confirm/Cancel 逻辑，适合对性能要求极致、无中间件依赖的场景（如核心支付系统）。

## 15\.如何保证接口的幂等性

保证接口幂等性的核心是：**无论接口被重复调用多少次（比如网络重试、前端重复提交、消息队列重试），最终结果都一致，不会出现重复创建资源、重复扣减库存、重复计费等问题**。

**1\.前端层面：减少重复请求**

**按钮置灰 / 禁用**

**表单防重复提交**

**2\.后端层面：核心方案**

**（1）基于「唯一标识」去重（最常用，适配大多数场景）**

核心思路：给每次 “有效请求” 分配一个唯一标识（业务唯一 ID 或请求唯一 ID），后端通过该标识判断是否已处理，已处理则直接返回结果，未处理则执行业务逻辑。

**（2）基于「数据库约束」去重（最彻底，防脏数据）**

利用数据库的「唯一索引 / 主键」特性，避免重复插入数据 —— 即使重复请求到达数据库，也会因唯一约束报错，后端捕获报错后返回成功（幂等响应）。

**\(3\) 基于「状态机」幂等（适配有状态流转的接口）**

若接口对应的业务数据有明确的「状态流转规则」（如订单：待支付→已支付→已发货→已完成），通过状态判断是否允许重复操作 —— 只有处于 “可操作状态” 时才执行，否则直接返回结果。

**\(4\) 基于「分布式锁」幂等（高并发场景）**

在高并发场景下（如秒杀），用分布式锁保证同一时间只有一个请求能执行业务逻辑，避免并发导致的重复问题（配合其他方案使用，如唯一 ID \+ 分布式锁）。
